# 用原生 hook 改游戏逻辑：几条踩过才知道的原则

这里记的不是「怎么写 arm64 hook」（那在 `hook.cpp`），而是**改哪一层、什么时候改、改完会连带什么**。
每一条都对应一次真实的翻车。

---

## 1. 先确认「目标层」真的有那个条件

最费时间的错不是 hook 写错，是 hook 打在了根本不参与判定的那一层。

同一个语义（例如「队伍里必须有某个角色」）在游戏里往往有两个互不相干的位置：

- **位置 A**：入口准入（剧情/事件管理器的条件列表）→ 走 `XxxManager.CheckCondition*`；
- **位置 B**：流程内部的判断节点（`判断存在标记 → 需要伙伴`、`进入某区域 → 需要伙伴`）
  → 走条件节点自己的 override，**裸函数调用**，不经过管理器。

只改 A 的表现是「入口放行了，但流程一走到 B 就断」，看起来像「改没生效」。

**怎么确认**：在候选 hook 里把参数结构的指针、图名、节点类名、条件 id 全打出来。
如果某个 hook 里那个字段恒为空（例如入口节点的 `conditionPort` 是空的），说明它不是判定点，换层。

## 2. 改条件判断：走基类，别恒真

两个子类 override 长成这样才能接管「只丢掉队友那条判断」：

```
子类(io,line):  if (!CheckAllConnectNodeAction(self, io, line)) return false;   ← 队友判断
                return base.CheckAllConnectNode(io, line);                      ← 尾调用基类
```

所以 hook 里**直接调基类实现**（把 `self` 压进 `line` 再 `CheckAllExceptSelf`）就等价于
「只跳过子类那一条，线上其它条件照常检查」。

反过来，`return true` 会让「条件节点」变成**随时满足**：

- 剧情里的 Hold 节点立刻通过；
- `StoryManager.ContinueArrange` ↔ `HoldNode.OnActive` 在同一帧互相递归；
- 几千层后原生栈溢出，进程直接消失（Android 是 SIGSEGV，logcat 里只有 `Fatal signal 11`）。

判据是「你会不会改变 line 的语义」：走基类不会，恒真会。

## 3. 放宽条件必须配两个兜底

条件被放宽之后，游戏里原本靠「条件为假」实现的一次性语义全部失效：

| 现象 | 兜底 |
|---|---|
| 同一段剧情反复触发 | Hold 节点有自己的「已成功过」标志（`checkSucessTimes`），但 `CheckCondition()` 不读它 → 判定为真且 times≠0 时压回 false，每个 Hold 只放行一次 |
| 深层递归爆栈 | 在递归必经点（`ContinueArrange`）按 `__thread` 计数限深，超限就丢弃这一层；下一帧从 0 开始，进度不会被永久堵死 |

限深不要用「同一对象每秒 N 次」那种闸门 —— 递归时每层命中的是不同实例，各自都能放行，总深度照样爆。

## 4. 「指针型拦截」的初始化时机：谁填指针，谁负责早解析

有一类改动不 hook 逻辑函数，而是 hook 一个**容器查询**（`HashSet<T>.Contains`），
靠「传进来的容器指针 == 我记住的那个集合」来认目标：

```c
if (set == g_enable_set || set == g_visible_set) return 1;
```

这类写法的**全部风险在初始化**：那几个集合指针是运行时从存档对象里解出来的
（`单例 → 存档 → 管理器 → 字段`），解出来之前它们恒为 NULL，比对永远不成立，
**拦截等于没装**。

真实表现：某个功能「要先去某个界面点一遍才生效」，因为只有那条路径解析过指针。

**规则**：把解析函数挂到**所有会用到它的入口**上，而不是只挂在当初开发时那条路径上；
并且用一个 `ensure_save(force)` 分成两档频率：

- `force=0`：未就绪时每 200ms 试一次，就绪后只做一次指针比较（热路径用）；
- `force=1`：低频入口（界面初始化、存档切换）无条件重解析 —— 换档后指针会变，不刷新就会打旧档。

## 5. 共享泛型方法里不要碰 il2cpp

`HashSet<T>.Contains`、`List<T>.Add` 这类方法在 IL2CPP 里只有一个共享实现，
**全游戏所有泛型实例都走它**，包括资源/存档加载期间的后台线程。

在这类 hook 里调 `il2cpp` 的 API（尤其 `MonoSingleton.get_Instance`、解引用 Unity 对象）
等于在工作线程碰托管运行时 —— 崩法随机，难复现。

**只读自己缓存的指针，不做解析**；解析放到主线程的 UI 方法里。

## 6. 「拿不到」不要静默兜底

`find_class(namespace, name)` 这类查找，命名空间传空、名字拼错、程序集不在，都只是返回 0。
如果调用方在 0 时「保守地返回一个默认值」继续跑，错误就被彻底藏起来了。

真实案例：查角色管理器时命名空间传了空串 → 恒为 0 → 「从未入队」判定恒返回 0（当作已入队）
→ 规则看起来「完全没生效」，但日志干干净净。三个版本之后才发现是查找失败。

**兜底可以有，但必须打日志**，并且日志要能区分「查到但结果如此」和「根本没查到」。

## 7. 按名字/图名做规则时，缓存必须带 TTL

很多规则要读「当前所在剧情图的名字」再决定放不放宽。读字符串、走指针链很贵，
放热路径上会卡，所以要做缓存 —— 但**入队状态、任务状态会变**，
永久缓存会让「条件满足之后」永远不再判定。

用 3 秒 TTL 的定长数组（节点指针 → 结果 + 时间戳）就够：热路径命中率高，状态变化最多延迟 3 秒。

## 8. 偏移是「量」出来的，不是猜的

同类对象相邻字段常常只差 8 字节（`backPack` / `dropOnDeadBackPack` / `stealBackPack`），
同一个 `partnerID` 在桌面端是 `+0x48`、在另一处结构里是 `+0x58`。
**每一端都要重新标定，并且用「读出来的值合不合理」验证**
（例如读角色 id：出现 `10084` 这种量级就对了，出现 `0` 或 `0x7f...` 就是偏移错了）。

## 9. 验证闭环：日志 + 装机时间 + 一次真实操作

- 打印一行带版本号的启动日志，`head -1 <log>` 就能确认跑的是哪一版；
- `dumpsys package <包名> | grep lastUpdateTime` 确认装上了（不是「以为装上了」）；
- 改功能的验证要靠**真实操作触发那条路径**，再回头看日志里预期的那几行有没有出现 ——
  「功能看起来正常」和「这条 hook 真的跑了」是两件事。
